# RFC 0010：增加 kq——用 jq 探索自描述的知识图

- 状态：**已完成实现与验收，获授权合入**；保留现有知识工具。
- 立项：[issue #34](https://github.com/hh9527/dsh-oks/issues/34)。
- 实施分支：`rfc/0010-knowledge-jq`（交付后清理）。
- 创建日期：2026-10-16。
- 关系：复用 [RFC 0009](./0009-wasm-toolset.md) 的纯 jaq 求值器；
  本次增加知识访问能力，保持现有数据加工、查询校验与执行、报告和来源链契约。

## 一、动机与范围

当前知识访问由 `oks_info`、`oks_search`、`oks_references` 分别提供单词条读取、词汇检索和反向引用。
这些工具给出了固定的访问粒度；组合筛选、批量关联和多步探索，需要 agent 多次调用并在上下文中拼接结果。

拟增加 `kq`，定位为**固定以当前工作区知识图为输入的专用 `jq_transform`**：
插件提供知识和通用求值能力，知识入口解释自身结构，agent 用 jq 选择阅读和发现路径。
知识整体留在执行侧，只有程序选出的结果进入模型上下文。

首版用于试用和观察，范围如下：

- 增加 `kq`，通过独立文件提供 jq 程序。
- 提供自描述的知识输入，统一以 `.[.index]` 启动发现。
- 支持知识装载后反复查询，在求值器中复用已解析的知识值。
- 保留现有三个知识工具与 `va_ask`，暂不决定工具退场。
- `kq` 专注读取和探索；数据物化与业务查询仍由各自工具承担。

## 二、启动协议与知识输入

### 最小启动协议

`kq` 的程序直接接收知识对象 `K`，程序里的 `.` 就是 `K`。
固定的启动协议只有三条：

1. `K` 是 JSON 对象。
2. `K.index` 是一个非空字符串，指向 `K` 中存在的顶层属性。
3. `K[K.index]` 是自述入口，说明知识如何组织，以及如何继续发现和读取。

首次探索从下面的程序开始：

```jq
.[.index]
```

入口应保持简短，描述结构和后续入口；大段知识通过引用继续访问。
工具提示词只讲启动协议、程序提交与结果语义。词条类别、字段、寻址方法、关系含义和查询意图的
表达方法，由知识文档自己声明，agent 读后获得。

### 首版装配方式

当前知识服务已有名为 `index` 的节点。外层启动指针与原始节点应分层保存，避免占用同一属性。
首版由插件将服务发现声明和节点原文装配为下列知识对象：

```json
{
  "index": "guide",
  "guide": {
    "说明": "discovery 是服务声明的发现契约；documents 是原始知识 key 到节点全文的映射。",
    "起点": "读取 .documents.index，获得领域入口；读取 .discovery，了解服务声明的发现方式。",
    "寻址": "将读到的知识 key 作为 documents 的对象键，原样读取对应词条。",
    "关联": "节点 links 中的 key 指向 documents 中的词条，关系含义以知识声明为准。"
  },
  "discovery": {},
  "documents": {
    "index": {},
    "Dataset/alarms": {},
    "Measure/alarms/count": {}
  }
}
```

示例中的空对象代表服务返回的完整内容；实际装配时应保留原始字段和值，不做摘要、截断或重命名。
`discovery` 保存发现路由成功响应中的声明对象，`documents` 保存各个 `Document.Found` 节点。
服务调用的 trace 和响应包装不进入词条正文。

`guide` 是插件生成的访问说明，负责解释这层装配；领域知识和业务语义来自服务原文。
`documents` 等路径是首版入口所声明的组织方式，通用 `kq` 执行层仅依赖最小启动协议。
知识发布方式演进时，可由新的自述入口解释新的组织方式。

### 收集边界

复用当前 `buildRetrievalIndex` 的发现过程：从 `index` 和 discovery 的 `roots` 出发，
沿节点 `links` 与 Index 的 `detail.schemas` 读取可达节点，按原始 key 去重。
目前该过程读完节点后仅保留派生索引；拟改为同时保留节点原文，供 `kq` 使用。

这份图的范围是**服务发现契约公开的可达知识**。入口或引用无法解析时，装载明确失败，
避免把残缺图当作完整结果提供给 agent。知识发布方应保证拟公开的知识均可从发现入口到达。
不可达内容的全量枚举需要知识服务另行提供导出能力，不属于首版承诺。

## 三、工具契约

工具名为 `kq`，首版仅接受一个可选参数：

```json
{
  "byFile": "knowledge_query.jq"
}
```

- 给出 `byFile`：读取 `.work/` 下的 `.jq` 文件，在知识对象上执行该程序。
- 省略 `byFile`：执行默认程序 `.[.index]`，返回自述入口；`kq({})` 即首次发现。
- 路径、文件大小、扩展名和错误定位沿用当前 jq 程序文件的规则。
- 文件程序读取一次；实际执行和诊断使用同一份源码及其文件名。
- 参数仅收 `byFile`，不引入 `inputs`、`pick` 或 `save`。投影与筛选直接写进 jq 程序。

程序通过 `work_write` 写入文件，再交给 `kq`，沿用 jq 代码与工具调用 JSON 分离的方式。
`kq` 与 `jq_transform` 共用纯 jaq 能力集；知识作为输入值进入，程序通过 JSON 访问关系，
求值过程中不隐式调用知识服务。

### 成功结果与失败

成功结果采用统一的值流收集规则：一个输出为该值，多个输出为数组，零输出为空数组。
结构化回执为：

```json
{
  "ok": true,
  "outputs": 1,
  "data": {}
}
```

`outputs` 区分“一个数组值”和“多个输出”；`data` 为完整结果。
采用与 `jq_transform` 相同的求值输出保护和最终回执大小限制，当前最终回执上限为 16 KiB。
求值到上限或回执超限时，返回明确的结构化错误，引导 agent 缩小投影、筛选、聚合或分段读取，
不给出半份成功结果。知识输入整体的大小不以进入上下文的预算衡量。

程序语法、运行时错误和超时沿用现有求值错误机制；文件程序的诊断包含文件名与引擎给出的定位。
知识装载错误应与程序错误区分，说明是工作区、发现过程还是启动协议失败。
日志记录知识身份、程序来源、耗时与结果数量，不把整份知识写进日志或回执。

首版查询结果只用于阅读与推理，不自动落成数据材料，也不新增来源链节点。
后续若要将知识查询结果作为报告的数据输入，应另行定义物化与来源记录，避免用手抄结果替代来源。

## 四、装载一次，反复查询

当前 `runJaq` 虽然复用 worker 与 Wasm 实例，但每次仍序列化输入、跨线程发送，并在引擎中重新解析。
只缓存 JS 对象无法实现本方案要求的输入复用。

拟在 Wasm 实例内保留已解析的知识值，由内部 handle 引用。
每个实例对同一知识只装载一次，后续程序通过 handle 求值；这些细节由插件管理。

`kq` 按知识身份（模型内容哈希 + domain）持有独立的求值 worker 与 Wasm 实例，
相同知识可跨会话共享这一实例。`jq_transform` 保留现有执行路径，与知识求值实例分开。
模型更新或求值超时时，只替换对应的知识求值实例，其他知识与数据加工不受影响。

```text
首次 kq → 收集并装配 K → single flight 装载到当前实例 → 保存 handle
后续 kq → 复用 handle 执行程序 → 返回结果
实例重建 → handle 与初始化记录一起失效 → 下次重新装载
```

- 内容哈希、发现声明与节点正文必须来自同一份已装载模型；装载身份固定后复用该快照。
  模型更新时销毁对应的 Wasm 实例，知识值与 handle 随实例一起回收；新实例装载新模型的知识。
  本方案不增加磁盘文件热更新机制。
- 在当前实例内按知识身份合并初始化：并发调用共享同一 Promise，成功后保存 handle，失败后允许重试。
  现有 `singleFlight` 完成后会移除 Promise，需配合成功结果缓存。
- 每次程序从同一份不可变知识值开始，后续调用只传程序、文件名和 handle，省去整图传输与解析。
- 知识值与 handle 在所属实例内常驻，生命周期与实例一致，无需单独的释放操作、引用计数或淘汰策略。
  worker 超时终止或 Wasm trap 重建时，一并清掉该实例的初始化记录；下一次调用按需重新装载。
  已失败的调用照常报告失败，旧 handle 只用于创建它的实例。

缓存只改变输入的装载成本。相同知识、程序与引擎得到相同结果，查询之间没有可变的共享分析状态。
现有 `jq_transform` 的逐次输入执行路径继续保留；两条路径共用程序编译、求值和错误语义。

## 五、探索示例与工具分工

agent 首次调用 `kq({})`，按入口得知首版结构后，可将以下程序分别写进 `.work/` 执行。
下面的 key 是示例，实际查询使用知识返回的 key。

读取领域入口：

```jq
.documents.index
```

按文本寻找候选，只返回 key 与说明，避免把整个词条集合送入上下文：

```jq
.documents
| to_entries[]
| select(.value | tostring | contains("告警"))
| {key, description: .value.description}
```

一次读取目标及其直接关联：

```jq
.documents as $docs
| $docs["Measure/alarms/count"] as $node
| {
    node: $node,
    related: [
      $node.links[]?
      | {relation: .type, node: $docs[.key]}
    ]
  }
```

自行查找反向引用：

```jq
.documents
| to_entries[]
| select(any(.value.links[]?; .key == "Measure/alarms/count"))
| {key, node: .value}
```

这些是 agent 发现结构后编写的程序，工具执行层不内置类别筛选、全文搜索或反向引用函数。
常用访问示例可放在知识入口或其引用文档中，agent 可以参考后调整。

`va_ask` 继续负责用户说法到领域词汇的语义对齐。它使用的词汇仍由服务的 vocabulary 声明派生，
与 `kq` 共用同一次知识收集。助手返回词汇线索后，主 agent 可通过 `kq` 检索并阅读原始声明。
查询 Intent 的规范 ID 与表达规则以知识声明为准，校验和执行仍经过现有工具。

## 六、实施与验收建议

建议按以下顺序实施：

1. 将知识原文收集与词汇、引用索引派生分开；保留原始节点，装配自述入口，复用现有索引与 VA。
2. 为 Rust 引擎、worker 和宿主增加知识装载与按 handle 求值路径，初始化由 single flight 合并，
   按知识身份持有独立 worker 与实例，知识与 handle 常驻其中；保留现有逐次输入路径。
3. 注册 `kq`，复用程序文件、结果收集与输出保护逻辑；提示词补充默认入口和探索方式。
4. 使用实际问题比较访问路径、往返次数和结果质量，再评估现有知识工具如何收敛。

实现需覆盖以下验收场景：

- 默认调用准确返回入口；缺入口、悬空启动指针和知识收集失败均明确报错。
- 已有 `index` 节点及其他节点原文完整保留，key 与引用可解析，原有知识工具和 VA 继续工作。
- 文件程序能完成读取、筛选、关联和反向引用；词条内容与原知识服务逐项一致。
- 一个数组值、多值和零输出的结果语义正确；超限结果明确失败，语法错带文件定位。
- 同一知识连续查询只收集一次、在稳定实例中只解析一次；并发首次访问同样只装载一次。
- 不同模型或 domain 相互隔离；程序修改输入结构后，下一次查询仍读到原始知识。
- 超时、trap 重建后旧 handle 和初始化记录一起失效，后续调用能重新装载。
- 某份知识更新、超时或实例重建时，其他知识的实例与 handle、`jq_transform` 的执行均不受影响。
- 文档缓存路径与逐次输入路径对同一 JSON 和程序产生相同的结果与错误语义。

首版完成的判据是：agent 能从唯一启动协议发现知识结构，自主组合访问路径，
并在多次查询中复用同一份已解析知识，而现有查询和报告能力保持各自的契约。
