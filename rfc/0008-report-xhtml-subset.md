# RFC 0008：报告正文改用 XHTML 子集——读回即缩水（草案）

- 状态：**草案**，工具接口及细节待评审。
- 立项：[issue #21](https://github.com/hh9527/dsh-oks/issues/21)。0007 已用于落盘命名，本方案编号为 0008。
- 关系：在 [RFC 0005](./0005-data-records-and-report-provenance.md) 的数据封装与来源链之上增加正文层，
  沿用 [RFC 0007](./0007-material-naming.md) 的材料命名；沿用 [RFC 0006](./0006-artifact-ledger.md) 管理报告，缩水样本不另设账本类别。

## 一、动机与定位

当前报告正文采用 Markdown 子集，图表通过独占一行的材料路径引用。来源链解释数据如何产生，
但正文缺少可机械识别的数据引用与解读边界，也没有明确保存章节组织和分析意图。

本方案将正文改为 XHTML 子集，读回完整报告时机械形成**缩水样本视角（柔性模板）**：
去除结构区中的实际图表、数值展示与观点解读，保留章节、意图及全部底层材料。

复用由原草案的“标槽位、填参数、实例化”收敛为“阅读样本、参考后重新创作”。
意图在缩水时完整保留；历史方法供参考，重新创作时可以调整章节、查询、加工路径与图表 spec。
样本不承诺自动重跑或复现原执行。

**完整数据溯源是本次改造的硬约束**：所有 `data-oks-ref` 引用的数据，包括图表与结论中的单个数值，
都必须可追到完整上游来源链和实际执行的 jq 源码。源码存储方式改变、数据投影与报告缩水均不能削弱该能力。

缩水不是一份独立产物，而是**把报告当输入来读**时的物化行为（见 §3、§5）：作者标了 `data-oks-shrink`
的元素内容在读模型中被清空，`data-oks-ref` 按 §5 处理，其余内容保留——边界由作者在创作时决定，不靠事后判断。

## 二、创作与复用

```text
业务问题 → 探索取数与加工 → 选择分析与图表 → 组织正文并说明意图
       → 校验与渲染 → 完整报告 → 读回物化〔缩水样本视角〕
       → 阅读、理解与参考 → 围绕新数据探索 → 重新创作完整报告
```

探索允许先观察数据形状、采样与统计，再决定下一步。最终报告收录被采用的分析及真实来源链，
未采用的探索分支无需全部进入报告。来源与加工记录由工具带入，Agent 编写表达意图和解读。

取数与加工继续使用现有数据封装，jq 执行通过 `byFile` 读取独立文件。
报告保存完整来源链、实际执行的 jq 源码、最终展示数据与 spec，不嵌入中间输出。

## 三、报告载体：元数据与结构两个区

最终交付物为自足的 `artifacts/<…>.report.html`，主体形态如下：

```html
<html>
  <body>
    <script type="application/json" id="oks-metadata">
      { "origin": {}, "assets": {}, "items": {} }
    </script>
    <article>…结构区…</article>
  </body>
</html>
```

- **元数据区**：`origin` 保存来源链；`assets` 是资源名到内容的映射，jq 源码作为其中的字符串资源；
  `items` 是以 ID 为 key 的展示项映射，保存最终展示数据、图表 spec 及来源关联。
- **结构／表达区**：`article` 保存章节、意图注释、图表位置、图注、数据展示和解读。
  通过 `data-oks-ref` 引用 `items`，集中管理底层材料，避免逐图复制来源链。

元数据区由 `oks_report` 从引用材料自动生成，Agent 只编写结构区及提供引用材料的绑定信息，
不手写 `origin`、`assets` 或 `items`。

来源链沿用 `{ root, nodes }` 节点表共享上游。jq 资源与来源节点的关联及其传播规则见下文；items 与数据来源的对应见 §4。
原先独立的 jq 代码区合并进元数据区，不再增加专用 `pre` 源码协议。

### 内部读模型：按需物化

**物化是内部行为，对外只有 `report.html` 这一种形态**：物化文件的名字与落点不进契约，随时可丢弃、
可重建。

`.report.html` 可以像其它材料一样作为 `jq_transform` 的输入（例如
`inputs: { k1: "artifacts/…report.html" }`）：工具在计算前完成物化，jq 看到的形状与其它材料同形——
`{ meta, origin, data }`：

| 字段 | 内容 |
|---|---|
| `meta` | 报告自述（name / kind = report / at / title / category…） |
| `origin` | 来源链 `{ root, nodes }` |
| `data.structure` | **缩水后**的结构区（XHTML 序列化字符串，含意图注释） |
| `data.items` | ID → 展示项（最终展示数据、图表 spec、来源关联） |
| `data.assets` | 资源 ID → 内容（含该次实际执行的 jq 源码） |

物化时执行 §5 的缩水规则，因此这份读模型**就是样本视角**，不再另产一份样本资产，也不单独进账本。
需要给人查看时，可按需将该视角渲染为 HTML。
两条实现纪律：**随源失效**（源 HTML 变了就不得再用旧结果，宁可当场重建）；**不作为读入入口**
（读入入口始终是 `artifacts/…report.html`）。

### 与现有生成和读回链路衔接

现有 `oks_report` 已从图表材料收集最终数据与 spec，合并来源链并增加报告组装节点，
通过报表级 JSON 块保存 `{ origin, data }`。当前 `data` 为 `{ chapters, plainTables, items }`，
其中 `items` 是按正文顺序排列的数组。报告自述 `meta` 已有独立承载位置。

本方案将报告元数据调整为 `{ origin, assets, items }`，`items` 改为报告内具名映射；
章节摘要由完整的 `structure` 取代，图表编号仍由渲染器按正文顺序生成，不能用编号充当稳定引用 ID。
结构区增加单根 `article`：章节、分析正文和图表位于其中；页面标题栏、生成时间、目录和页脚由工具在其外生成，
报告标题等自述由 `meta` 保存。物化只提取 `article`，不把外壳重复收入结构。

现有读入路径为 `readProduct` → `parseArtifactOrigin`，已直接在内存中把报告归一为
`{ meta, origin, data }` 并交给 jq，无需先落 JSON 文件。本方案在报告分支增加元数据解析、
`article` 提取和缩水即可；物化采用内存解析，不新增缓存文件或缓存协议。
现有 `reportChapters` 通过正则提取标题和图表归属，不能承担完整结构和注释的保留；
应使用能保留注释的结构解析器，不以正则执行 XHTML 子树清理。

加工数据、查询结果、给定数据、SVG 和表格材料保持现有封装与来源记录。
本方案改变报告正文、报告元数据及报告读回，不扩展普通材料的业务 data 结构。

### 报告专用的源码资源归档

所有资产读模型保持 **`{ meta, origin, data }`**。加工数据和图表材料已经通过 `origin` 内嵌记录完整来源，
继续保留加工节点的实际 `snip`、来源文件信息和上游依赖，不增加 `assets` 或 `value` 包装。

**只有报告 HTML 使用 `assets`**：报告需要全内联，并汇聚共享上游与共享代码。
组装时先按现有规则合并完整来源链，再将来源节点中的 `snip` 提取为报告资源，
以 `byFile: "asset://<key>"` 引用资源。报告内源码唯一存放在 `assets`，不在相同节点里重复保存程序正文。
这属于报告序列化方式，不是通用来源记录的改造。

报告读模型为：

```json
{
  "meta": {},
  "origin": { "root": "report-node", "nodes": {} },
  "data": {
    "assets": {},
    "items": {},
    "structure": "<article>…缩水后的结构…</article>"
  }
}
```

HTML 元数据为 `{ origin, assets, items }`，物化时将资源与展示项放进 `data` 并补入缩水后的 `structure`。
其中 `origin` 采用报告中的资源引用表示；每个 `byFile: "asset://<key>"` 都必须在 `data.assets` 中可解析。

资源 key 为 `<原文件名主干>-<源码 SHA-256 前 16 位>`。取原文件名并去掉扩展名，
哈希按来源节点记录的实际执行源码 UTF-8 字节计算，不额外格式化。
例如 `monthly-sales.jq` 对应 `monthly-sales-a3f82c91d047b6e2`。
同文件名主干且同源码共享资源，不同文件名主干即使源码相同也保留不同 key；
相同 key 对应不同内容时报错。工具生成的程序使用固定逻辑文件名，例如 `identity.jq`。
同一上游节点只保留一份，多个节点引用同一 key 时源码也只保存一份。

报告中的加工节点示例：

```json
{
  "kind": "transform",
  "byFile": "asset://monthly-sales-a3f82c91d047b6e2"
}
```

`asset://` 是协议保留的内联资源命名空间，后面的 key 精确对应报告 `assets` 的键。
资源引用与工作区文件路径由专用解析器区分：工作区路径解析器明确拒绝 `asset://` 前缀，
资源解析失败时报错，不能回退为文件读取。隔离由协议保证，不依赖文件系统能否创建相似名称。
原执行文件说明继续独立保存，供追溯及来源记录还原。
使用 `byFile` 而非另设 `program`，让 Agent 可以将方法引用及对应资源一起复制到新报告，
以相同表达复用历史方法。复制时必须携带资源，缺失资源校验报错。
复制方法不代表再次执行：新数据的来源记录必须由本次实际操作产生。
实际执行工具仍从独立 jq 文件读取，资源提取到文件由程序完成。

### 从报告继续加工的溯源

报告的来源记录有两个明确的序列化步骤：**组装时提取源码，进入通用来源合并前还原源码**。
后续 jq 工具读取报告时，先从完整读模型解析所有 `byFile: "asset://<key>"`，还原为现有节点的 `snip`，
作为本次加工的上游来源；再按业务 `root` 或 `pick` 选取交给程序的数据。
jq 仍可读取包含 `assets` 的报告读模型，工具内部携带的上游来源则使用现有完整记录表示。

新的加工结果按现有格式保存，origin 中内嵌上游实际源码，不需要另带报告 assets。
再次出图或组装报告时继续沿用原溯源机制；只有组装为 HTML 时再次集中归档代码。
还原必须在业务切片前完成，不能因为只读取一个数值而丢失代码和上游节点。

提取与还原必须可逆：恢复后的节点记录与提取前一致，包括实际程序、文件说明、动机与输入关系。
保留原来源节点 ID，不因报告资源 key 重算数据节点身份；现有节点身份与冲突检查继续基于还原后的完整记录。
报告引用态节点不直接混入普通来源链合并，先还原，再执行现有 `mergeChains` / `appendNode`，
避免同一节点的两种序列化表示造成冲突。缺资源或同 ID 异记录均报错。

### jq 与安全序列化

Agent 继续写独立 jq 文件并通过 `byFile` 执行。报告从 origin 中已有的实际执行记录提取源码，
不在渲染时重新读取可能已修改的同路径文件。需要复用资源时，由程序提取为文件；
JSON 转义由程序完成，Agent 不手写 origin、assets 或 JSON 内嵌 jq。

HTML 中的 JSON 必须安全序列化，例如将 `<` 写为 `\u003c`，避免资源中的 `</script>` 提前结束元数据块。
JSON 解析后应还原原始源码内容。

## 四、结构区与引用语法

结构区采用严格 XML、单根 `article` 的 XHTML 子集，使用原生章节、标题、段落、列表、图表、
强调、链接及代码展示元素。允许的元素和属性白名单待实现时收敛。

意图直接用 XML 注释表达，放在对应章节或内容前面，说明这一部分想回答什么、为什么这样组织。
注释保存在文件中，供工具或源码阅读，浏览器不将它显示为正文。读写与渲染流程必须保留注释；
缩水仅删除清空范围内的注释，范围外的注释保留。注释文本遵守 XML 内部不能出现 `--` 的约束。

### item 引用与值摘取

- **`data-oks-ref="<id>"`**：只填本报告 `items` 的 key，精确引用整个 item，不携带路径。
- **`data-oks-pick="<dot-path>"`**：仅用于带 `data-oks-ref` 的 `span`，从该 item 中摘取展示值。
  路径必须以 `.` 开头，`.` 表示 item 根值；省略时取整个 item，最终值须为标量。
- 路径只支持对象字段及数组下标，第一版不支持字段名本身含 `.`，不引入 jq 表达式、通配符或函数。
- 对象上的数字路径段按字符串键访问，数组上的数字路径段按非负整数下标访问。
- 空引用或空路径无效；找不到 item 与找不到路径分别报错，合法 `null` 与路径不存在区分。
- `figure` 引用完整 item，禁止 `data-oks-pick`；其他元素也不使用该摘取属性。
  只有 `data-oks-pick` 而没有 `data-oks-ref` 的元素校验报错。

例如：

```xml
<figure data-oks-ref="monthly-sales">…内联图表…</figure>
<span data-oks-ref="summary" data-oks-pick=".growth">12%</span>
<span data-oks-ref="summary" data-oks-pick=".regions.0.name">华东</span>
<span data-oks-ref="summary" data-oks-pick=".">…根值展示…</span>
```

`data-oks-ref` 同时标明引用和缩水边界。图表必须带有该属性，正文数值可用带引用的 `span` 表达。
观点、评价和结论不必制造数据引用，直接用 `data-oks-shrink` 标记。
### 报告提交与数据绑定

`oks_report` 保留现有 `name`、`category`、`note` 和 `spec.title`、`spec.subtitle`；
`spec.markdown` 改为 `spec.xhtml`，新增 `spec.inputs`。提交形态为：

```json
{
  "name": "alarm_report",
  "spec": {
    "title": "告警分析",
    "xhtml": "<article><!-- 展示总量与分布。 --><p>告警总数：<span data-oks-ref=\"alarms\" data-oks-pick=\".rowCount\"></span></p><figure data-oks-ref=\"by-level\"></figure><!-- 解释分布。 --><p data-oks-shrink=\"\">高等级告警值得关注。</p></article>",
    "inputs": {
      "alarms": { "src": ".oks/data/summary.tr.json", "root": ".data" },
      "by-level": { "src": ".oks/figures/levels.pie.svg", "root": ".data" }
    }
  }
}
```

示例路径代表工具回执中的真实材料路径。输入值也可简写为 `src` 字符串，默认 `root` 为 `.data`，
沿用现有 jq 工具具名输入的参数风格。`root` 是封装中的点路径，不是来源节点 ID。
`spec.inputs` 的 key 直接成为 `items` 的 key；重复使用同一数据时可在正文多次引用同一个 key。
材料统一通过现有路径校验和读取入口解析，Agent 不直接填写数据、来源或源码。

`items[id]` **就是该绑定选出的 JSON 值**，不额外套 `data` 或混入 `root` 等保留字段：
普通加工结果绑定 `.data` 后可以是 `{ rowCount: 100 }`，图表及表格的默认数据沿用现有 `{ rows, spec }`。
这样 `.rowCount` 始终从 item 的业务根解析，也不会与工具添加的元字段冲突。
报告在渲染与缩水前收集结构区全部引用，包括位于 `data-oks-shrink` 元素内部的引用；
不能从缩水后的结构反推输入集合。报告只收入结构区实际引用的绑定；缺少绑定、未使用绑定及路径不存在均报错，避免静默遗漏或收入多余材料。

### inputs 以数据依赖组织

来源记录中的 `inputs` 表达**使用了哪些输入数据**，不是图表序号、标题或布局关系。
报告组装节点的 `inputs[id]` 指向同名绑定材料的 `origin.root`，
并以 `inputPaths[id]` 保存从该材料封装选取数据的点路径。
其中 `inputPaths` 是与 `inputs` 配套的操作字段；所有带输入切片的加工记录也采用同一规则保存实际选择路径。

因此 `items[id]` 的来源根由 `origin.nodes[origin.root].inputs[id]` 查得，
绑定切片由同一节点的 `inputPaths[id]` 查得。来源关联不混入业务数据。
图表项使用图表材料的来源根，追溯其最终数据；是否以饼图、折线图展示仍由 item 的 spec 描述。
所有引用项都纳入组装节点，包括只出现在结论中的一个数值，不以“图 N／表 N”命名数据依赖。

### 引用渲染

`span` 的引用值由程序按 `data-oks-ref` 定位 item，再按可选 `data-oks-pick` 摘取并覆盖元素内容，Agent 可以提交空 `span`，手写值不作为最终数据依据。
首版字符串原样显示，数字与布尔值用 JSON 标量文本显示，`null` 显示为 `null`；
对象和数组不直接填入 `span`，应先通过加工得到所需标量。单位、百分号等固定文本放在 `span` 外，
需要舍入或计算时先生成有来源记录的加工数据，首版不增加格式表达式。

`figure` 必须引用完整的图或表展示件，不接受 `data-oks-pick` 或自选 `root`；
报告读取已生成的 SVG 或表格并内联，复用现有展示件渲染链路，不因本 RFC 自动重跑图表 spec。
图注由作者写在 figure 中，工具保留它并生成编号；作者不用填写 SVG 或表格内容。
内联后移除展示件重复携带的来源与数据块，统一由报告元数据保存。
其他带引用的原生元素可以作为作者组织的内容容器，工具验证引用但不根据标签猜测展示方式。

现有 `parsePath` / `selectPath` 服务 jq 工具的 `root` 和 `pick`，只支持对象逐键访问，不能直接满足数组下标规则。
`data-oks-pick` 的路径解析需补齐数组访问，或提取共享的点路径实现；若同时调整 jq 工具，需明确其行为变化并验证现有用法。

### 所有引用数据均可溯源

沿用已有 `origin.root` 与节点 `inputs` 的数据依赖关系，源码提取到 `assets` 仅改变其承载方式。
`items` 收录所有实际被引用的数据，不限于图表；仅在结论中使用一次的数值，也必须带入其完整来源链。
绑定数据切片后仍保留原来源根及全部上游节点，路径选择不能成为无来源的字面值。

例如：

```xml
<p>本期告警总数为 <span data-oks-ref="alarms" data-oks-pick=".rowCount">100</span>。</p>
```

此引用的追溯路径为：

```text
data-oks-ref="alarms" data-oks-pick=".rowCount"
  → items["alarms"] 的 .rowCount
  → 报告组装节点 inputs["alarms"] 指向的数据来源 root
  → inputPaths["alarms"] 记录的绑定切片
  → origin.nodes 中的完整上游依赖、Intent、实际来源与加工动机
  → 加工节点的 byFile: "asset://<key>" 引用
  → data.assets 中实际执行的 jq 源码
```

追溯解释的是该值所选自的数据及其生产过程，不要求字段级依赖分析，也不保存中间输出或承诺重新执行。

缩水后数值变为 `??`，引用与摘取属性、最终数据、来源节点及源码资源不变，仍可沿同一路径追溯。
后续从报告取数、加工、出图及再次组装报告时，来源链与资源继续完整传播；旧材料回收不影响这条追溯路径。

### XHTML 最小边界

首版作者元素白名单：`article`、`section`、`h1` 至 `h3`、`p`、`div`、`span`、
`figure`、`figcaption`、`table`、`caption`、`thead`、`tbody`、`tfoot`、`tr`、`th`、`td`、
`ul`、`ol`、`li`、`blockquote`、`pre`、`code`、`strong`、`em`、`a`、`br`、`hr`。
XML 注释允许保留。属性白名单包括 `id`、`class`、`title`、`lang`、`data-oks-ref`、`data-oks-pick`、`data-oks-shrink`、
链接的 `href` 及表格的 `colspan`、`rowspan`、`scope`；数值与链接属性需校验其合法值。
作者链接允许文内锚点及 `http` / `https`，不允许可执行协议、事件属性、脚本或作者内嵌 SVG。
CSS 和页面外壳由工具生成，作者不提交 `style` 或任意未知属性。

作者 XHTML 的白名单校验发生在内联之前；工具生成的 SVG 不套用作者标签白名单，
但沿用现有 SVG 清理规则。报告的整体 HTML 用 HTML 解析器读取，提取 `article` 后按 DOM 执行缩水，
输出良构的 XHTML；SVG 在引用容器内被清空，不要求整个页面外壳作为严格 XML 解析。
保留的是节点、属性和清空范围外的文本及注释内容，不要求原始引号、实体拼写或字节序列不变。

## 五、机械缩水规则

缩水在**物化时**对结构区执行（物化即缩水），规则只按属性是否存在，不解析内容语义：

1. 有 **`data-oks-shrink`**：清空全部子节点，优先于下一条规则；不区分属性值。
2. 否则有 **`data-oks-ref`**：`span` 的全部子节点替换为纯文本 **`??`**，其他元素清空全部子节点。
3. 元素本身及全部属性保留；**其余信息一律保留**。

嵌套标记由最外层操作决定，被清除的子树无需继续处理。实现时可使用 `textContent = "??"` 替换文本。
缩水无需解析 item 引用或摘取路径，也不猜测内容语义；重复缩水结果相同。

意图注释、需保留的标题与图注由作者放在清空范围之外——**不做元素类型的特例**（图注留不留，取决于作者
把标记写在哪）。所有图表都带引用；观点、评价、结论等本次解读都标记缩水；**未标记的内容一律保留在
结构上**（它就构成样本的内容），漏标因此只会让样本多带一块解读，需要内容核对。

**结构区中图表及其中的数据被清空，元数据区的最终展示数据仍然保留。**
来源链、`assets`、`items` 和 spec 均不改写，也不额外删除历史材料路径。
历史路径随材料回收而失效是正常情况；报告读取与追溯依赖内嵌材料，而不是重新打开旧路径。
因此缩水是去展示、去解读，不是去数据或脱敏；样本保留本次分析的底层材料供参考，
不会因缩水而降低数据敏感度，分享时沿用完整报告的数据边界。

## 六、缩水前后示例

完整报告的结构区：

```xml
<article id="sales-report">
  <!-- 先观察整体趋势，再比较区域差异，最后检查变化的可能来源。 -->
  <h1>区域销售变化分析</h1>
  <section id="overview">
    <!-- 判断销售规模如何变化，以及变化是否集中在某些时段。 -->
    <h2>整体销售趋势</h2>
    <p>本期同比变化 <span data-oks-ref="summary" data-oks-pick=".growth">12%</span>。</p>
    <!-- 展示各月销售额，定位值得进一步分析的月份。 -->
    <figure id="sales-trend" data-oks-ref="monthly-sales">
      <figcaption>月度销售趋势</figcaption>
      <div>…渲染器生成的内联图表…</div>
    </figure>
    <!-- 结合趋势解释变化的主要原因。 -->
    <p data-oks-shrink="">增长主要集中在三月。</p>
  </section>
</article>
```

缩水后：

```xml
<article id="sales-report">
  <!-- 先观察整体趋势，再比较区域差异，最后检查变化的可能来源。 -->
  <h1>区域销售变化分析</h1>
  <section id="overview">
    <!-- 判断销售规模如何变化，以及变化是否集中在某些时段。 -->
    <h2>整体销售趋势</h2>
    <p>本期同比变化 <span data-oks-ref="summary" data-oks-pick=".growth">??</span>。</p>
    <!-- 展示各月销售额，定位值得进一步分析的月份。 -->
    <figure id="sales-trend" data-oks-ref="monthly-sales"></figure>
    <!-- 结合趋势解释变化的主要原因。 -->
    <p data-oks-shrink=""></p>
  </section>
</article>
```

例中的图注位于被清空的图内，随图内容一起清除；需要保留的表达目的由外部注释说明。
元数据区保持不变，仍可从 `monthly-sales` 阅读数据、spec 和来源链，再追到实际 jq 源码。

## 七、校验与复用边界

校验覆盖 XML 良构、白名单、唯一 ID、引用语法、item 与路径存在性，以及来源与资源关联。
拟返回结构化错误 `{ code, message, line, column, element }` 并附修正建议。
完整报告要求展示内容齐备，缩水样本允许引用容器为空或为 `??`；二者共享同一引用协议。
具体工具接口待定。

渲染器负责组装元数据、解析引用和内联图表；Agent 负责意图注释与解读的缩水标记。
不额外要求固定槽位、参数实例化或另一套源码载体；不保存额外原文备份，也不提供原文恢复。

**对外契约是一份自足的 HTML**：人打开它读到完整的图表、数值与解读，意图注释保存在源码中；工具把它当输入读时，
拿到的是**骨架 + 全部底层材料**——被标 `data-oks-shrink` 的解读内容按设计已清空。两种视角的差异是
设计，不是读取失败；因此"改一份旧报告"的路径是"读它 → 重新创作"，不提供原文恢复。

复用时，Agent 阅读样本中的结构与意图，参考保存的查询、加工代码、数据和 spec，
围绕新问题重新探索与创作。新报告的来源链来自本次真实操作，历史方法不能冒充新执行记录。
旧自足报告仍可打开；仅对具备相应标记的新报告保证机械缩水。

## 八、推进与待定事项

先用一份真实报告验证“创作 → 渲染 → 读回物化〔缩水样本视角〕→ 阅读后重新创作”的最小闭环，
再扩展工具能力，避免提前引入完整模板协议。该闭环的验收应包含以下可复现对照：

- `data-oks-shrink` 优先清空，包括与 `data-oks-ref` 同时存在的 `span`。
- 仅有 `data-oks-ref` 的 `span` 变为 `??`，其他元素清空；嵌套按最外层决定。
- 元素及属性、清空范围外的注释与内容保持，元数据不变，重复缩水结果相同。
- 渲染保留意图注释，源码资源序列化与读回内容一致。
- 对象数字键、数组下标、合法 `null` 和不存在路径按约定区分。
- 所有产物采用统一封装并能作为 jq 输入；从报告加工后，上游源码还原到普通产物的 origin 中，完整保留且无需 assets。
- `span` 显示值来自绑定数据并覆盖作者手写值；图表从真实展示件内联，缺少或多余绑定时报错。
- 图表与非图表绑定均纳入来源链；报告内资源去重、引用闭合，源码提取后还原的节点记录一致。
- 同时输入一份报告与其上游普通材料，共享节点在源码还原后正常合并，身份冲突和缺失资源时报错。
- 结论中 `data-oks-ref="alarms"` 配合 `data-oks-pick=".rowCount"` 的单值引用可追到 item 来源根、全部上游记录及实际 jq 源码，
  缩水后仅展示值变为 `??`，追溯路径仍完整。
- 验证“报告读回 → 取单值或切片 → 再加工 → 再出图／报告”，并在原材料回收后核对来源与资源仍自足。

漏标通过内容核对发现，首版不增加未标记文本块的默认告警。

1. 在工具 schema、读写类型和提示词中落实上述绑定、items 和数据来源关系。
2. 结构解析器、属性合法值检查与工具生成 SVG 的处理实现。
3. 报告源码提取与还原、资源 key 生成，以及还原后沿用现有节点身份和来源合并。
4. HTML 生成、内部物化及按需展示样本视角的工具接口。
5. 结构解析器选择及容量上限对来源链、资源和展示数据整体的处理。
