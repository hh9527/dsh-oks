# RFC 0002：用 typst 统一图表渲染与报告

- 状态：**正式立项**
- 立项：<https://github.com/hh9527/dsh-oks/issues/2>
- 分支：`impl-rfc/0002`
- 创建日期：2026-10-10
- 关系：**技术选型上取代 [`rfc/0001`](./0001-conversation-charts.md)**（那里面"图表在服务端用 d3 自绘"的路线不再采用）；
  `rfc/0001` 仍然有效的是**产物形态**部分——图落成工作区文件、回执给一行 markdown、图出现在回答正文里。

## 决策

图表渲染统一走 **typst**：用它的 JS/WASM 运行时（`@myriaddreamin/typst.ts`）与图表包
（`lilaq` 覆盖统计图、`cetz-plot` 覆盖业务图、`cetz` 兜底示意图）。

`bar` / `line` / `column` / `pie` / `area` 全部由**同一套 lowering**（业务规格 + 结果行 → typst 源码）
产出，再编译成 SVG（进回答）或 PDF（未来的报告）。

**契约、取数层、来源标识、落盘与回执都不变**：`oks_chart` 的调用形状与结果文件格式保持不变，
换掉的只是最底下那层"怎么把数画成图"。

## 为什么改为这条路线

`rfc/0001` 选的是"服务端用 d3 的两个纯计算包自己拼 SVG"，首期也跑通了。它有两个天花板：

1. **图型成本线性增长**：每加一种图元都要自己写布局、刻度、图例、标签避让。目标是十几种图型，
   继续走下去等于维护一个自研图表库——而这一层与我们的业务价值无关；
2. **PDF 报告要另起一套**：报告需要排版（章节、分页、目录、图表与文字混排），d3 只画图，
   排版还得再引一套，并且两套之间要靠中间格式对齐。

typst 同时解决这两件事：它本身就是排版系统，**图是文档的一部分**——于是"回答里的图"与
"报告里的图"同源，未来产出 PDF 不需要第二套技术。

**可行性已在 issue #2 上探明**（分支 `impl-rfc/0002` 的前身）：

- WASM 运行时在 Node 里可用，不需要 DOM；
- **离线可复现**：包与字体都在 `dist/` 内，初始化期间零网络请求；
- **中文自带**：系统里没有任何中文字体，我们把中文字体与 typst 的 17 个默认字体一起本地化；
- **性能**：首次初始化约 0.9 秒（含 WASM 实例化与字体加载），之后单张图几十毫秒。

## 实施范围

**一、迁移（把已有图元搬到新路线）**

- `bar`（横条）与 `line`（多序列折线）从 d3 自绘迁到 typst；
- 删除 `src/svg.ts` 与 `d3-scale` / `d3-shape` 依赖——产物里只剩一条渲染路径；
- **不变的部分**：`spec` 的字段与语义、`src` / `data` 两条取数路径、来源标识、
  `.data/` 落盘与 `![标题](路径)` 回执。

**二、补齐新图元**

- `pie`：饼图（`cetz-plot` 的 piechart，或 lilaq 的等价物）；
- `area`：面积图（lilaq 的折线填充）。

**三、保留的既有约束**

- 沿用数据顺序（不做隐式排序与聚合）；
- 缺失组合留空位；
- 图里带系统来源标识；
- SVG 只含图形本体（去掉 typst 的交互层），能在宿主 `<img>` 里渲染；
- 画布占满页宽，并按 pt→px 换算物理尺寸。

## 性能实测（本机，2026-10-10）

| 项 | 结果 |
|---|---|
| 首次初始化（WASM 实例化 + 字体） | 约 **0.9 秒**；插件加载时**后台预热**，用户不必等 |
| 单张图（预热后） | 简单图约 **76 ms**；15 张串行平均 **154 ms/张** |
| 并发 9 张 | **657 ms** 全部成功，无状态污染 |
| 常驻内存 | rss 约 **460 MB**（WASM 与字体常驻，服务端的一次性成本） |

## 风险与边界

- **包体积**：`dist/` 目前约 46 MB（编译器 WASM 28 MB、字体 17 MB、包缓存 1.2 MB），
  跨架构通用、服务端只加载一次，已确认可接受；字体以后加字重还会变大；
- **常驻内存**：约 460 MB rss——WASM 运行时与字体常驻的代价，见上表；
- **上游警告**：初始化时 stderr 会出现两条 wasm-bindgen 的旧签名提示，上游行为、不影响功能；
- **图型能力边界**：typst 图表包覆盖不到的图型（若有），再评估是否自己补 lowering；
- **不做的部分**：交互式图表（宿主只在 `<img>` 里渲染静态图）、报告生成（留给下一期）。
