# RFC 0005：数据封装与报表自足——完整来源链与最终展示数据

- 状态：**草案（未评审、未实施）**。本文提出变更方向与核心契约；具体编码、工具参数细节和容量限制在评审时确定。当前行为以代码为准。
- 立项：待定，尚未开 issue。实施建议采用**档 3**：涉及存储落点、数据表达、工具面和交付物契约，需要分阶段验收。
- 分支：待定，实施时建立本地与远程分支。
- 创建日期：2026-10-12。
- 关系：承接 [RFC 0004](./0004-artifact-timeline.md)，将产出层从三类文件平铺演进为内部数据、图、报表各归其位，并使报表携带完整的数据来源链。沿用 ECharts 渲染与 HTML 报告形态。

## 问题与目标

当前查询结果、图和报表都写入 `artifacts/`。查询结果保存 Intent 与数据行，图可以来自查询结果，也可以由 agent 直接填写数据。`oks_jaq_result` 返回求值结果，多步加工的中间结果尚未成为可继续引用的封装数据。

报表已经能够独立显示：图被内联为 SVG，文件可以离开工作区打开。但解释数字所需的查询意图、加工代码、输入关系和动机仍散落在工作区与会话里。工作区是可回收的临时车间，报表则会被下载、分享和讨论；只保存画面不足以说明数据怎么来的。

本次变更要统一查询与加工的数据封装，由工具自动延续来源链。**报表交付完整生产过程与最终展示数据，中间输出留在工作区。** 来源链记录数据的完整加工过程：可以沿最终数据向上理解每一次 Intent 和 jq snip、输入关系及操作动机。

目标是还原报告中的数据来源，支持解释与溯源。报表不携带各步中间输出和完整执行环境，不承诺复现执行；来源信息也不自动证明数据真实或业务判断正确。

## 决策

### 1. 将内部材料与交付物分开存放

| 落点 | 内容 | 生命周期 |
|---|---|---|
| `.oks/data/` | 查询和物化加工产生的封装数据 | 可回收的内部材料 |
| `.oks/charts/` | 图及其最终输入、来源信息 | 可回收的内部材料 |
| `artifacts/` | 自包含 HTML 报表 | 按保活规则清理，用户可显式保留 |

`.oks/state.db` 继续保存报表的保留状态。内部材料的回收针对数据与图目录，保留状态独立管理。删除整个 `.oks/` 会丢失保留状态，但已经交付的报表内容仍然完整。

图是报表的组成材料，显式保留只适用于报表。清单和下载沿用报表这一口径。

### 2. 查询与加工统一使用 `{ origin, data }`

每份封装的数据由两部分构成：

- `origin`：产生这份数据的操作及完整上游来源链，由工具生成。
- `data`：这次操作的结果，可以是标量、对象、数组或嵌套结构。

封装统一来源表达，结果保持通用 JSON 形状。列描述等表格信息仅在适用时提供，具体承载位置和编码在评审时确定。

查询工具负责建立来源链起点。`origin` 至少保存实际提交并通过校验的 Intent、操作动机，以及工具实际取得的数据来源信息。相对时间在提交前解析成 Intent 中的绝对边界。查询结果也写成同一封装，后续 jq 工具从其 `data` 读取数据。

Intent 记录“请求查什么”，`source` 记录“执行时实际用了什么”，例如实际数据来源标识、revision 和数据窗口。两者分别表达请求与执行事实，便于审计时对照；source 只保存工具实际取得的信息，未知信息明确为未知，具体最低字段在评审时确定。

加工工具负责延续来源链。它读取各输入的封装，将其 `data` 交给表达式，并把各输入的 `origin` 连同本次实际执行的 snip、动机和具名输入关系组成新的 `origin`。上游的数据输出不进入新 origin。

以下嵌套示例仅表达 origin 的逻辑关系；文件内的推荐编码见第 7 节，准确字段尚待评审：

```js
// 查询输出
{
  origin: {
    kind: 'query',
    intent: submittedIntent,
    motivation: queryMotivation,
    source: observedSourceInfo
  },
  data: queryResult
}

// 加工输出
{
  origin: {
    kind: 'transform',
    motivation: transformMotivation,
    snip: executedSnip,
    inputs: {
      events: eventsEnvelope.origin,
      thresholds: thresholdsEnvelope.origin
    }
  },
  data: transformResult
}
```

输入名明确表达哪个来源对应哪份数据。来源信息随输出复制，工作区路径可以作为背景信息，但解释来源链所需的信息必须存在于 origin 内部。上游文件被回收后，已经生成的输出仍保有完整来路。

### 3. 将 `oks_jaq_result` 拆成两个工具

两个工具共用具名输入和 jq snip 的求值语义，以结果的去向区分用途：

| 工具 | 用途 | 输出去向 |
|---|---|---|
| `jq_transform` | 检索、抽样、统计、摘要及临时计算，帮助 agent 理解数据 | 按容量限制返回给 agent |
| `jq_transform_into` | 将加工结果保存，供后续加工或报表消费 | 写入 `.oks/data/`，返回引用与摘要 |

`jq_transform_into({ target, motivation, inputs, snip })` 的概念流程为：

1. 解析具名 inputs，读取每份输入的 `{ origin, data }`。
2. 向 snip 提供按输入名绑定的数据，其求值范围是各输入的 data。
3. 执行 snip，取得加工结果。
4. 工具自动生成包含本次操作和各输入 origin 的新 origin。
5. 将 `{ origin: 新来源链, data: 加工结果 }` 写入 target，成功后返回数据引用及形状摘要。

`target` 表达输出落点，其命名与路径约束在评审时确定。agent 提供 snip 和 motivation，来源结构由工具根据实际读取的输入与实际执行的操作建立，snip 只负责计算 data。

`jq_transform` 使用相同的数据绑定和求值能力，agent 可以查看字段、理解嵌套结构、获取采样值、统计分布或寻找异常。探索性调用不自动成为后续来源链的一部分，也无需为每次读取创建文件。若其结果要成为报表的数据依据，应通过 `jq_transform_into` 物化，由后续消费者引用封装数据。

两个工具允许通用 JSON 结果。jq 的多值输出如何收集、如何区分单个数组值与多个输出值，以及零输出的表达，在评审时统一确定；求值与物化必须保持一致语义。

### 4. 让 agent 在物化数据上持续探索与加工

`.oks/data/` 的中间输出是下一步操作的输入，也供 agent 通过 `jq_transform` 理解形状、获取样本和摘要。agent 可以根据读取结果继续编写 snip，再用 `jq_transform_into` 保存下一步结果。

例如：查询得到事件数组；加工得到含统计值与分组明细的对象；agent 查看对象的字段和分组样本；最后分别生成用于统计值展示和分组图表的数据。统计对象可以作为完整中间结果保存，无需提前强行转成表格。

加工采用显式输入上的确定性计算。业务时间值由 Intent 或数据显式提供，记录产生时间仅作为元信息。求值器允许能力限定为输入 JSON 上的计算，环境能力约束的实现方式在评审时确定；不以提示词代替执行约束，也不承诺跨引擎版本复现。

### 5. 在报表消费边界约束展示结构

通用加工结果进入报表之前，需要转换为对应消费者可以利用的数据结构。图表可能要求行对象数组，表格要求表格结构，统计值展示要求对应的值结构；这些契约由消费入口定义和校验。

转换通过 `jq_transform_into` 完成，转换 snip 及输入关系进入来源链。原始查询结果已经满足展示要求时，可以直接引用。报表入口应明确报告形状不符，agent 可先用 `jq_transform` 检查，再加工成符合要求的封装数据。

`oks_chart` 收敛为只接受封装数据的 `src`，取消调用方直接填写 data。绘图时消费 data，保留 origin、最终输入与绘图规格，使图可交给报表使用。呈现过程中的排序、分箱等计算由实际绘图规格说明。

常量按用途进入：参考线或固定阈值可以作为绘图规格的一部分，随实际规格保存；参与统计、计算或作为对比数据展示的常量，应通过 snip 生成封装数据，使常量及其动机进入来源链。后一种用途需要支持无数据输入的 snip，例如 `inputs: {}`，其 origin 记录本次代码与动机；这类常量仍须符合展示消费结构。示意类现填图形不纳入本期工具面。常量在规格与数据之间的具体判定规则及参数形式，评审时明确。

正文中的数据表和统计值也应通过显式数据引用进入报表，具体关联或展示参数在评审时确定。自由叙述由 agent 撰写；生成器通过显式引用识别数据依据，不从自由文本猜测来源。

### 6. 报表携带完整来源链与最终展示数据

报表继续内联 SVG，并以与正文分离、可由工具读取的结构化块保存展示数据的封装。报表至少携带：

- 实际用于图表、表格和统计值展示的最终 data；
- 对应 origin 中每次查询的 Intent、每次加工的 jq snip、各步动机和完整输入关系；
- 展示项与数据的对应关系、绘图或展示规格。

**报表不复制上游中间输出。** 完整来源链指完整的操作过程与关系，最终展示数据指实际交给展示消费者的数据。探索时未被采用的读取调用不属于该来源链；若一份中间输出本身也被用来展示，它便同时属于报表的最终展示数据。

由于每份封装已经自带来源链，报表生成时可以直接复制它的 origin，无需重新遍历工作区中的上游文件。图携带的封装信息也应在报告组装时保留，不能只留下 SVG 画面。

来源信息应能回答：这个展示数据最初通过什么 Intent 取得，经过哪些 snip，各步使用了哪些输入，为什么执行这些操作。它支持还原来路，逐步复算所需的中间数据和执行环境不属于交付契约。

构建时核对当前消费的封装、来源信息和展示结构齐备，并检查容量。缺失或超限时明确失败，供调用方缩小范围；成功报表必须完整携带必要来源链和最终展示数据。

### 7. 以复制保证独立性

每次物化将上游 origin 带入当前输出，报表再携带最终封装。内部文件可以按目录与保活规则独立回收，不建立长期引用计数、依赖 GC 或重放入口。

多输入可能共享上游来源，来源链在结构上形成有向图。**推荐在每份文件的 origin 内使用节点表与根节点标识**：每个操作一个节点，具名输入引用文件内节点 ID，根节点指向产生当前 data 的操作。物化时合并输入节点表并加入当前操作，共享祖先按同一操作身份保留一个节点。节点引用在当前文件内闭合，不依赖上游路径。

嵌套复制便于直读，但体积会随链深与共享程度膨胀；节点表可以减少重复，代价是阅读时需要沿 ID 查找。推荐以读取工具提供易读视图，准确编码和身份冲突处理留待评审；无论采用哪种编码，文件都必须自身包含完整来源链。

记录标识一次操作，内容哈希用于核对保存内容。两次操作即使结果相同，也各自形成记录；操作身份和文件命名方式在评审时确定。

## 为什么选择这条路线

统一封装让查询、统计、摘要与后续加工共享一套来源表达，同时保留 JSON 的结构灵活性。数据形状在消费者边界约束，使加工能力可以服务分析与展示两种用途。

来源由工具随着实际执行自动生成，agent 无需事后补写操作链。origin 只携带生产过程，data 保存当前结果，既能在工作区继续加工，也能让最终交付物仅携带必要的展示数据。

报表是用户会带走的交付物，在构建时复制完整来路和最终数据，能避免它依赖可被回收的工作区。增加来源信息体积是获得独立性的代价，且不需要承担保存全部中间输出和复现环境的成本。

## 实施阶段与验收

### 阶段 1：目录与查询封装

迁移内部数据和图的落点，将查询结果改为 `{ origin, data }`，调整路径与清理规则。为查询加入动机输入，并由工具生成实际 Intent 和来源信息。

阶段验收：查询封装可读，origin 中 Intent 对应实际提交的请求，source 对应实际取得的执行事实，data 与实际结果一致；读取约束覆盖新目录与符号链接边界；回收内部材料不改变报表保留状态；认不出的文件保持原样。

### 阶段 2：两个 jq 工具与自动追踪

拆分读取与物化，建立具名输入、通用 JSON 求值和自动 origin 组装。

阶段验收：标量、嵌套对象、数组及多值输出遵循约定；agent 能查看形状和采样；多输入、两级以上加工的 snip、动机与输入关系准确记录；新 origin 含完整上游过程而无上游 data；删除祖先文件后仍能从最后的封装读出完整来源链；执行或保存失败产生明确回执。

### 阶段 3：展示结构与图

确定消费结构并校验，图只接受封装引用，保留最终输入、origin 和绘图规格。

阶段验收：统计对象可以经有记录的 snip 转换成展示结构；形状错误可检查并修正；直接填写图表数据的请求被拒绝；十种图元保持呈现能力；图离开工作区后仍含所用数据和完整来源信息；规格中的参考线被保存，snip 生成的常量对比数据具有完整封装。

### 阶段 4：报表来源链

加入图表、表格和统计值的数据关联，嵌入最终封装及展示关系，明确容量与失败行为。

阶段验收：清空内部数据与图目录后报表仍能显示，且能读出最终展示数据和每次 Intent/snip 的生产关系；共享输入关系正确，推荐节点表中的共享祖先仅存一份且节点引用在文件内闭合；祖先中间输出未嵌入；探索调用未被误纳入来源链；必要材料缺失或超限时明确失败。

### 阶段 5：界面、工具描述与文档收尾

同步清单、下载、右侧栏和技能文档，处理旧布局遗留文件。

阶段验收：插件与 UI 包的 `pnpm run check` 通过，profile `--dump-config` 零警告；重启后完成真机验收。尚未完成的真机行为明确标为待验证。

各阶段提交须有阶段性目的与验收记录，方案或进展变化在 issue 上汇报；完整目的达成后经人确认，以 squash 合入 `main`，再清理本地与远程分支。

## 评审时需要确定的细节

- origin 的准确字段、版本、source 的最低执行事实与操作身份；节点表、根节点和共享祖先的文件内编码及身份冲突处理。
- 通用 JSON 和查询单元的编码，表格元信息的位置；多值及零输出的求值与物化语义。
- inputs 绑定到 snip 的方式；两个工具的准确参数、target 命名与覆盖规则。
- 求值能力约束的实现方式，输入与输出容量、超时及截断回执。
- 图表、表格、统计值的消费结构，正文数据引用与展示的接口；参考线等规格常量与数据常量的判定规则，无输入 snip 的参数语义。
- SVG 与 HTML 中封装的保存、读取及安全转义，来源信息在报告组装时的保留方式。
- 单份封装、来源链、图和报表的容量上限及超限行为。
- 内部保活期限、清理触发点；旧布局文件的迁移或一次性清理方式。

## 风险与边界

来源链会随加工增长，多输入共享祖先还可能导致嵌套重复。需通过文件内编码和容量检查控制体积，完整性以交付文件自身包含必要过程为准。

当前输入可能在加工前被回收，工具需明确报告缺失；已经生成的封装可以脱离祖先文件继续解释来路。内部保活策略仍需覆盖通常的分析时间。

动机由 agent 提供，可能表达不准确；来源链也不能证明源数据真实。工具记录实际输入来源和执行代码，业务含义与结果正确性仍需单独判断。

本 RFC 确立“统一封装、自动来源链、最终展示数据”的核心契约。评审通过并立项后再进入实现。
