# RFC 0023：DARI 统一诊断与多位置类型检查

状态：草案。跟踪：https://github.com/hh9527/dsh-oks/issues/62

## 问题与目标

DARI 检查沿依赖图收集独立绑定的错误，但类型编译器遇到错误时通过异常中止当前表达式。一个 `fields` 对象中有多个互不依赖的错误时，通常需要多轮检查才能逐一发现。

解析、文档编译、类型检查和后端预检已有多处诊断数组与异常捕获，收集边界和错误传播方式不一致。本 RFC 定义统一的诊断协议，优先改善语法解析成功后的类型诊断；语法恢复在类型阶段验收后另行设计。

目标是在一次检查中报告能够独立判断的源码错误，保留准确位置，抑制由同一根因引起的连锁诊断，并继续检查不依赖失败结果的部分。检查不能读取业务行；存在错误时不能执行、渲染或发布结果。

## 诊断协议

一次检查拥有一个诊断收集器，各阶段通过显式接口报告诊断。接口至少支持 `report(diagnostic)`、创建检查点和判断检查点之后是否产生错误；具体 TypeScript 名称由实现确定。收集器以现有 `SourceDiagnostic` 的文件、阶段、消息、范围和关联位置为基础，内部区分错误与警告，必要时携带稳定的错误类别和所属绑定。

诊断属于本次检查及原始 `.dari` 源码，不附着于跨次执行缓存。报告顺序按原文件位置稳定排序，同位置的顺序有确定规则；重复诊断按结构化身份去重，不依赖消息文字判断是否为上游错误。并发分析不得让相同输入的输出顺序随完成时序变化。内部完整收集，公开回执继续限制展示数量并报告省略数。

源码不合法、类型不匹配和模型返回的可定位验证错误，通过诊断通道报告。取消、超时、资源耗尽和内部不变量损坏等不能安全继续的情况仍可中止；不得把这些故障伪装成普通源码诊断。已有异常边界可以在迁移期间将已知的用户错误转换为诊断；最终异常不是正常类型错误的主要通信方式。

## 类型错误传播

类型分析提供显式的错误结果，以下称 `ErrorType`。它表示该表达式的类型因已报告的错误不可用；不得与表示业务值在运行期才知道的 `UNKNOWN` 混用，也不等同于 `None`、`Never` 或一个合法的可空类型。

检查子表达式时：

- 独立子表达式分别检查并向同一收集器报告错误
- 依赖 `ErrorType` 的运算传播错误状态，不为同一根因再报告类型不匹配
- 对不依赖错误部分、仍可确定的问题继续报告诊断
- 可以保留局部结构供同一表达式中的独立检查使用；绑定整体有错误时，其公开类型状态为未就绪，下游绑定不把局部结构当作已通过的类型
- 错误结果不能生成可执行 SQL、调用模型取得依赖错误值的查询计划、写入成功类型基准或进入数据执行缓存

例如：

```dari
data result = select({from:{s:facts},fields:r=>({
  first:r.s.missing_first,
  second:r.s.missing_second,
  total:r.s.count + "invalid",
})});
```

当 `facts` 已知包含 `count:Int` 而不包含前两个字段时，一次检查应分别报告两个不存在的字段和数值与字符串相加的错误。若某个字段访问的输入自身已是 `ErrorType`，不再为该访问追加由此产生的“字段不存在”错误。其他独立绑定继续检查，依赖 `result` 的绑定显示未就绪。

对象字段、数组元素、函数参数和二元运算的独立子表达式应尽量继续检查。`select` 的来源、连接、过滤、投影、分组和排序具有依赖顺序：只在所需作用域和类型可确定时检查对应部分；无法确定的部分标记未就绪，不虚构表 schema。对于 `case_when`、`map_opt` 和模板条件，所有可独立判断的分支都要检查，不能依据运行期数据跳过检查。

## 阶段边界

语法和名称解析成功后，类型分析从模型 transform 得到的列 schema 推导类型，不取得业务行。`Known` 与 `Deferred` 继续描述值何时可用；错误类型独立描述检查失败。缺少 schema 的查询及其依赖保持未就绪，不以空表或猜测值继续推导。

检查模式可以构造用于诊断的局部结果，但只有整个相关计划无错误时才能提交有效的类型结果或 SQL 计划。SQL 参数、表和计划的构造不得因为尝试恢复而污染其他节点。`dari_resolve` 的检查与 `dari_check` 使用相同规则；整稿有错误时不进入业务读取、后处理、渲染或交付。运行期的数据完整性、schema、资源和基数检查仍独立执行。

公开回执沿用 `diagnostics`、`unresolved-node-types` 和 `inspect-node-types`。失败绑定及依赖它的未就绪节点列入 `unresolved-node-types`；独立成功绑定的类型仍可报告。类型基准按绑定更新，不把错误或局部类型写成成功状态。`inspect` 只重报已成功推导的类型，不改变诊断或执行状态。

## 推进顺序

1. 定义统一收集器、结构化诊断和错误类型，接入现有检查入口，保持对外回执及成功程序行为
2. 在语法解析成功的前提下，扩展表达式和关系运算的多位置类型检查，逐步覆盖对象、数组、函数、运算和 `select` 各部分
3. 完成类型阶段验收，核对真实模型下诊断质量、检查耗时和输出预算
4. 类型阶段验收后单独设计语法恢复：选择可靠的同步边界、错误节点及与类型检查的衔接，不在本 RFC 中承诺具体恢复范围

每个阶段以测试和可审查的阶段性交付推进；语法恢复不能以牺牲错误位置或制造大量误报为代价。

## 验收

- 同一 `fields` 内多个独立字段错误及其他独立类型错误一次报告，位置指向原始源码
- 同一错误只报告根因；错误类型的投影、算术、聚合和下游绑定不产生无依据的连锁诊断
- 独立绑定及同一表达式内不依赖错误结果的子表达式继续检查；非法绑定及其依赖保持未就绪
- 记录、数组、可空类型、左右连接、聚合、`map`、`union_all`、条件分支和图表类型覆盖成功及失败场景
- 检查不取得业务行；有错误的 `resolve` 不执行业务查询、数据后处理 SQL、渲染或交付，也不把错误结果写入成功缓存
- 成功程序的类型、排序、数值、来源及缓存语义与当前实现一致；取消、超时、资源限制和内部错误保持明确的终止行为
- 多错误输出顺序、去重、20 条公开回执上限与省略数量稳定；中文、特殊字符和多行源码位置准确
- 自动测试覆盖类型检查、DAG 状态和运行边界，并通过类型检查与完整回归；真实模型验证不依赖业务数据库

## 类型阶段验收记录

- `diagnostics-test.ts` 覆盖独立错误、错误类型传播、源码位置、取消和 SQL 准备边界；`draft-typed-test.ts`、`dari-if-test.ts` 和图表测试覆盖类型与成功程序行为
- `draft-tools-test.ts` 验证 `resolve` 出错时不读取业务行、不发布附件或交付消息；`check-receipt-test.ts` 验证类型基准、未就绪节点与 20 条回执上限
- 当前实现通过完整源码回归（48 个测试文件）和 TypeScript 类型检查。真实模型验证可通过 `experiments/analysis-execution/check-model.ts` 执行；脚本禁止访问业务执行器，并测量检查耗时和回执大小
- 类型阶段允许保留局部边界处对已知校验异常的转换；普通表达式错误主要经收集器和错误类型传播。语法恢复仍需另行设计，不能将目前的类型恢复当作语法恢复
