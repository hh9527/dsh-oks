# RFC 0007：材料与图表件的落盘命名——短后缀、图元进文件名、图表同目录

- 状态：**已完成**（实施已合入 `main`）。本文件是变更计划；当前事实以代码与 `README.md` 为准，
  实施结果与两处补充记在文末「实施结果」。
- 分支：`rfc/0007-material-naming`（本文件单独交付）
- 创建日期：2026-10-14
- 关系：**修订** [`rfc/0005`](./0005-data-records-and-report-provenance.md) 的"落点分层"
  （`.oks/data` · `.oks/charts` · `.oks/views` · `artifacts/`）——新的分层是
  `.oks/data`（材料）· `.oks/figures`（图表件）· `artifacts/`（报表）与 [`rfc/0006`](./0006-artifact-ledger.md)
  的清理范围（"是不是我们的文件"那条正则认哪些名字）。不改产物形态、不改来源链结构、不改渲染与
  读数据那条路。
- 前置观察：
  - 材料后缀偏长，且 `query` / `transform` / `data` 在文件名里重复表达了"我是材料"；
  - 图的 `.chart.svg` 说了类别、没说**是什么图**——要再点开或看回执才知道；
  - `.oks/charts/` 与 `.oks/views/` 把"给人看的展示件"拆成两处，而它们在概念上是一类（图表件），
    页签那块概览也早已把两者合并计数；
  - `derived.json` 只活在"是不是我们的文件"那条正则里：`ArtifactKind` 没有它，代码里也没人产出。

## 决策

**一、材料后缀取短名**

| 类别 | 新 | 旧 |
|---|---|---|
| 查询结果 | `.qres.json` | `.query.json` |
| agent 自填数据 | `.def.json` | `.data.json` |
| jq 加工结果 | `.tr.json` | `.transform.json` |

**二、图表件同目录（`.oks/figures/`），图的后缀带图元**

- 目录：图与表都落 **`.oks/figures/`**（`figures` 是文档语境里"图表"的通用词——
  "figures and tables"；类别仍是 `chart` 与 `table` 两种：**目录是伞，类别是伞骨**。取消
  `.oks/views/`，`.oks/charts/` 也不再作为图的家）。
- 图：`<时间>-<名>-<哈希>.<图元>.svg`；图元取自 `CHART_KINDS`（bar / line / column / pie / area /
  scatter / histogram / box / heatmap / radar）——文件名自己说清是什么图。
- 表：`<时间>-<名>-<哈希>.table.md`（不变）。
- `kind` 字段仍是 `'chart'`（清单、图标、来源链按类别稳定）；图元只进文件名。
- "是不是我们的文件"那条正则**由 `CHART_KINDS` 生成**：以后加图元不会再漏一处。

**三、老名字不再认**

写新名、也只认新名。老工作区里已有的 `.query.json` / `.transform.json` / `.data.json` /
`.chart.svg` / `.table.md` 从此是"不是我们的文件"：不清理、不被引用、不进清单。`derived.json`
一并从契约里消失。`artifacts/` 里的报表不受影响——报告自足，图与表在生成时已内联。

## 为什么不选另外两条路

- **双认老名（过渡期兼容）**：要多一条"老名也算我们的"判据，清理与占用的口径就得分老新两套；
  而这些老文件的生命周期只有几小时（材料按窗口自动回收），为它们留一层兼容不划算。
- **读到老名就改名迁移**：要连报告正文里的引用一起改，迁移本身还要动用户工作区里的文件；
  收益只是"少躺几个几小时后本来也会被清理的文件"。

## 迁移

没有迁移层。老文件留在原地，归入"认不出"的一类——与用户自己放进 `.oks/` 的文件同等对待
（不清理、不引用）。

## 实施范围（一次做完）

1. `results.ts`：目录常量（去掉 `VIEW_DIR`）、类别 → 目录/后缀映射、名字生成（图带图元）。
2. `state.ts`：`OURS` 由 `CHART_KINDS` 生成，后缀换新名，去掉 `derived`。
3. `tools.ts`：后缀判定的两处字面量（`.chart.svg` / `.table.md`）、回执里的路径、工具描述里的示例。
4. `chart/report.ts`：报告正文接受并解析的引用写法（`.oks/figures/<文件>.<图元>.svg` 与
   `<文件>.table.md`）。
5. 提示词与文档：`skill.md`（多处示例路径）、`README.md`（落点分层与工具表）、`locale/*.json`、
   `cordis.patch.yml` 的说明。
6. 页签：概览块"图表"一类读新目录（它本就把图与表合并计数，这里只是目录变了）。

## 验收

- 冒烟：新后缀与新图元名逐个出现（`qres` / `def` / `tr`，10 种图元抽样）；`OURS` 只认新名
  （老名文件既不被清理、也不被引用）；报告能引用同目录下的图与表并内联；保活与 `collect` 按新目录
  工作；概览块四类计数与新目录一致。
- 真机：重启后走一遍"查数 → 加工 → 出图 → 出表 → 出报告"，看目录、文件名与报告打开都正常。

## 风险与边界

- 老工作区里会留下若干"认不出"的老文件（可手删；`collect` 不再碰它们）。
- 已交付报告不受影响（自足）。
- 老会话上下文里的 `dataSrc` 指向老名字 → 需要重新取数（与本变更之前的清理行为同类）。

## 明确不做

- 不改 `artifacts/` 与 `.report.html`。
- 不改来源链（`{meta, origin, data}`）的形状与节点语义。
- 不为老名字提供读取或清理上的任何兼容。

## 实施结果（收口）

- 一次做完（没有兼容层要分层），改动落在 `packages/dsh-oks` 与 `packages/dsh-oks-ui` 两处。
- 验收：宿主冒烟 **326 / 0**（断言条数与改名前**一致**——不是靠删断言过关），界面 check 通过。
- 两处补充：
  1. `report/read.ts` 的读法分派原本按 `src.endsWith('.chart.svg')`；新命名下图是 `x.bar.svg`，
     会掉进"当 JSON 封装读"的分支报错——改为按 `nameParts(src).kind === 'chart'` 分派（复用
     `kindOfFile` 这一处映射）。这本就是改名该暴露的 bug，冒烟里"读图 / 读图的 origin"两条守着它。
  2. 本机 demo 工作区里没有需要迁移或额外删除的老文件：老材料在此前的一次手工清理里已被回收，只删掉了
     旧布局遗留的两个空目录（`.oks/charts`、`.oks/views`）。账本只登记报表，无悬挂行。
