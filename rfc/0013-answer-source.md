# RFC 0013：以 Markdown 为回答源码，全量求值数据处理流水线

- 状态：草案；整体方向已确认，协议细节待补齐；本文不包含实现授权。
- 创建日期：2026-10-19。
- 关系：复用 RFC 0005 的来源链、RFC 0008 的报告表达与读取，以及 RFC 0012 的数据加工能力。

## 一、动机与范围

目前，Agent 把业务思路留在会话中，把 Intent 放进工具参数，把 jq、XHTML 写成独立文件，
再手动搬运校验键与资产路径。修改分析时，还需自行判断哪些结果需要重新计算。

拟引入一份 `.work/<问题名>.md`，作为回答一个用户问题的源码。
Agent 探索、修改整份源码，工具全量求值其中的处理流程，逐步缓存并返回反馈。
普通文字回答和持久化报告共用这一过程，区别在于最终交付形式。

这份源码从业务问题寻求答案，组织“问题理解 → 分析方法 → 数据证据 → 结论与表达”。
领域知识、Schema 和工具的学习与发现属于 Agent 的准备活动，留在源码之外。
看到业务数据后新增查询、调整口径或进一步分组，则是求解过程，继续通过改稿表达。

主要内容包括：给定／自造数据、由 Intent 定义的查询、数据加工，以及最终 XHTML 答案模板。
本文拟增加一种编排方式，复用现有校验、执行、输入形状、预算与来源链。

## 二、文档分为 pipeline 与 assets

`pipeline` 用带 let binding 的流水线表达式连接处理步骤，`assets` 用独立代码块保存材料与程序。
Markdown 散文说明问题理解、分析理由和表达思路。

- `## pipeline` 节下有一个 `js` 代码块，定义完整处理流程。
- `## assets` 节下，每个资产通过代码块的 `name="..."` 属性命名。
- 资产正文按自身语言直接书写：JSON、jq、XHTML；流水线只引用其名字。

工具按 Markdown 语法树识别这两个区域、围栏与章节，不扫描代码内容猜测区域边界。
第一版要求这两个区域各一个；pipeline 的 `js` 标记用于语法高亮，实际语法与求值规则见第三节。
普通代码示例可写在其他章节，不进入流程；assets 下的具名代码块只作为资产解析。
围栏长度遵循 Markdown 规则，正文含围栏字符时可以使用更长围栏。

### 一个完整的结构示例

以下示例展示“查询 → 统计返回行数 → 在答案中引用”。
`<dataset id>` 须替换为领域声明的实际数据集，Intent 仍须通过实际模型校验。
`warningRows` 是示例给定阈值，不是查询服务的行数限制，也不是观测事实。

````md
# 本次查询的数据概览

先看本次返回规模，再判断是否需要进一步分组。这一行数只描述查询结果，不代表源数据总量。

## pipeline

```js
// 设定本次分析使用的参考阈值。
let threshold = data("threshold.json");
// 读取一批业务数据，了解后续分析的输入。
let facts = query("facts.intent.json");
// 统计本次返回行数，并与参考阈值比较。
let summary = jq("summary.jq", { facts, threshold });
// 用有来源的数字说明本次查询规模。
let answer = render_html("answer.xhtml", { summary });
answer
```

## assets

### 参考阈值

```json name="threshold.json"
{ "warningRows": 100 }
```

### 查询意图

```json name="facts.intent.json"
{
  "op": "Graph",
  "root": "d",
  "nodes": [{ "id": "d", "entity": "<dataset id>" }],
  "edges": [],
  "select": [],
  "limit": 500
}
```

### 汇总方法

```jq name="summary.jq"
(.facts.rows | length) as $count
| {rowCount: $count, exceedsReference: ($count > .threshold.warningRows)}
```

### 最终答案模板

```xhtml name="answer.xhtml"
<article>
  <!-- 说明本次查询规模，为进一步分析提供依据。 -->
  <p>本次返回 <span data-oks-ref="summary" data-oks-pick=".rowCount"></span> 行。</p>
</article>
```
````

一次修改可以只变更一个资产，也可以调整 pipeline 的分析路径；工具始终处理整份源码。
程序正文保持原始语法，Markdown 的 JSON／jq／XHTML 不进入 JS 字符串或模板字符串。

## 三、流水线表达式与依赖

### let binding 的求值模型

流水线由依次绑定名字的表达式和末尾结果表达式组成：

```js
let d1 = data("d1.json");
let a = jq("a.jq", { d1 });
let b = jq("b.jq", { d1: d1.a[0].a, a });
let result = render_html("answer.xhtml", { a, b });
result
```

每个 binding 定义一个不可变的处理节点，名字在当前流水线内唯一，先定义后引用。
末尾表达式指定整个流水线的结果。第一版限定为一个已绑定名字，结果须为最终答案。
即使某个绑定未被末尾结果引用，它仍参与本次求值，可作为业务探索分支。

这是一种借用 JS 熟悉写法的流水线表达式语言，`let` 表示绑定，整个表达式有一个结果。
工具解析其结构，建立 DAG，再执行或复用各步计算；不通过 JS 引擎求值任意脚本。
第一版的语法范围为：

- `let 名字 = 固定操作调用;`，及末尾的结果名字。
- 字符串字面量引用资产；对象字面量传递具名上游结果。
- 对象支持简写 `{ d1 }` 和显式键名 `{ facts: d1 }`；键按字面处理。
- 输入值为已绑定名字或从该名字出发的静态路径，例如 `d1.a[0].a`。
- 行注释说明该步业务意图；格式、换行与缩进用于可读性。

赋值更新、循环、条件、任意函数、动态资产名、动态路径及任意文件写入不进入首版语法。
字段选择和数组下标可在调用参数中表达；筛选、遍历、形状摘要、分支计算与聚合由 jq 资产承担。
完整词法和语法仍需补齐；标准 JS 解析器可以作为实现候选，允许结构由本协议验证。

### 变量引用就是依赖

例如 `jq("a.jq", { d1, d2 })` 中，变量引用 `d1`、`d2` 自动形成上游边，
对象的键同时定义程序输入为 `{d1: d1.data, d2: d2.data}`。
用 `{ facts: d1 }` 时，程序通过 `.facts` 访问同一份数据。
数据加工省略输入对象或传 `{}` 时看到空对象。

输入对象也可以直接投影上游数据：

```js
let a = jq("a.jq", { d1: d1.a[0].a, d2 });
```

路径以节点的 `.data` 为起点，因此上式程序看到的是
`{d1: d1.data.a[0].a, d2: d2.data}`，依赖仍是 `d1`、`d2`。
静态路径支持字段访问、字符串字面量键和非负整数数组下标，如 `.a`、`["a"]`、`[0]`；
字段缺失、数组越界或容器类型不符时明确报错，不把取值失败悄悄转成缺失输入。
下标与键在解析时固定，不执行动态路径表达式。

这样，流水线中的输入投影直接由参数表达，取消独立的 `project` 操作与对应规则资产。
`Shape`、`Map` 等已有投影能力在源码外的 `oks_data` 中继续适用；
流水线需要同类结果时用 jq 计算，本轮不因此修改单步工具的投影契约。

工具从流水线表达式构建依赖，不扫描 jq、XHTML 或散文猜测依赖，也无需额外的依赖清单。
顺序绑定本身排除了前向引用与循环，非法引用在执行前定位到 pipeline 中的原位置。

三个名字空间各有职责：

| 名字 | 作用 |
| --- | --- |
| binding 名，如 `a` | 当前流水线中的节点身份 |
| 输入对象键，如 `facts` | jq 输入或模板绑定所见的名字 |
| asset 名，如 `a.jq` | 当前文档中程序或材料的引用身份 |

同一个 asset 可以被多个 binding 使用，形成多次不同输入的处理。
binding 名、asset 名都不直接充当缓存键或来源链节点 ID。

## 四、操作与 assets 契约

建议首先用固定操作组合现有能力：

| 操作 | asset 正文 | 输入与结果 |
| --- | --- | --- |
| `data("d1.json")` | JSON 数据 | 给定值、常量、假设或演示数据，产生带来源的数据结果 |
| `query("facts.intent.json")` | JSON Intent | 内部校验并只读执行，产生含 `{rows, columns}` 的查询结果 |
| `jq("a.jq", { ... })` | jq 程序 | 接收具名数据对象，恰好产生一个 JSON 值 |
| `render_figure("a.figure.json", { data: a })` | JSON 图表／表格规格 | 复用现有渲染能力，生成带数据与来源的展示件 |
| `render_html("answer.xhtml", { ... })` | XHTML 模板 | 组装最终答案，具名输入绑定正文的引用 |

上述资产名使用文件名形状表示内容类型，实际是**文档内资源名**，不自动解析为工作区文件。
assets 的 `name` 全文唯一，采用带扩展名的单个文件名；流水线操作按实际调用检查正文语言与内容类型。
例如 `query` 要求 JSON Intent，`jq` 要求 jq 程序，`render_html` 要求 XHTML。
缺失资源、重名或类型错配在执行前明确报错，不把拼错的名字解释为外部路径。

第一版允许尚未引用的资产留在文档中作为备选，它们不产生计算节点。
实际被引用的资产须通过对应操作的内容检查；重复使用一个资产不要求复制代码块。
工具可在内部适配现有文件接口，对 Agent 不要求把各资产再写成独立文件。

`render_figure` 的数据角色由固定输入键确定：`data` 是主数据，关系图可选 `nodes` 是节点数据。
这些值也是依赖变量，不再单独声明 `src` 或依赖名列表。
`render_html` 的对象键直接对应 `data-oks-ref`；标量提取继续使用 `data-oks-pick`。
沿用报告绑定的双向检查：正文引用须有绑定，每个绑定也须在正文使用。

`data` 的材料性质进入来源记录，查询结果及加工值通过变量流转，不由 Agent 重新抄成给定数据。
源数据查询、加工和展示继续遵守现有行数、输出预算、确定性及来源规则。
时间来自显式捕获的上下文材料；首版如何向业务流水线提供该材料，需在实现前明确，不能依靠 jq 读取隐式当前时间。

知识发现、Schema 探索、词汇助手等继续使用源码外的工具交互。
本轮不定义知识浏览操作或通用工具调用节点；模型参与查询校验与执行时的实际身份仍须可追踪。

## 五、全量求值与探索反馈

工具暂称 `oks_run_answer`，参数建议为：

```ts
{
  src: ".work/question.md",
  delivery?: "reply" | "artifact",
  refresh?: boolean
}
```

`delivery` 默认为 `reply`，决定最终结果如何交付，不改变业务分析的依赖关系。
一次执行固定读取时的源码快照；执行中的修改属于下一轮。

执行顺序为：

1. 解析完整 Markdown、pipeline 与具名 assets，固定源码摘要。
2. 检查流水线语法、名字、操作签名、资产引用及结果类型，构建 DAG。
3. 编译可提前检查的 jq，检查静态规格与 XHTML；查询沿用领域校验与一致性校验键。
4. 按依赖关系处理全部 binding，命中缓存则复用，未命中则执行。
5. 检查动态输入形状、模板绑定与标量取值，返回本轮反馈和最终表达。

静态结构错误在产生新资产前返回。首版可以按绑定顺序串行处理，保持执行逻辑简单。
某节点运行失败，其下游为 `blocked`，独立分支继续，以便一轮获得更多反馈。
失败、取消、超时和预算超限均不产生成功缓存项，独立成功的计算可在下轮复用。
全部 binding 成功后，末尾结果才标记为可交付。

全量求值针对完整表达式，缓存是工具的内部执行优化。
Agent 观察结果后调整分析路径，通过改写源码再提交完成，调用参数不提供片段选择。

## 六、逐步缓存与数据新鲜度

每个 binding 都是独立的缓存单元。计算缓存依据操作、实际 asset 内容、具名输入值以及相关执行环境。
仅 asset 名相同不足以命中；同名内容变化会影响对应计算。

- 修改 jq asset，重新处理使用它的 binding，并按实际输入检查其下游。
- 修改 XHTML，复用查询与加工结果，重新组织最终表达。
- 仅重命名变量或资产、调整注释和排版，程序与实际输入不变时可复用计算。
- 对象输入键参与计算身份：把 `.facts` 改成 `.rows` 是输入接口变化，即使值相同也须重新判定。
- 参数使用静态路径时，取值完成后用实际选中的输入判断计算缓存；未选中的数据变化不必触发纯计算。
- 模型、执行器、渲染器版本或相关配置变化，使受影响的缓存失效。

实际输入值用于判断计算复用，输入的来源身份用于验证本轮来源装配。
相同数据具有不同来路时，可以复用纯计算，但须继承本轮真实上游；不能直接返回带旧来源的最终封装。
缓存保存的计算结果与本轮执行记录分开，变量名、资产名、业务说明的变化不能伪造重新查询事实。
首版可用更保守的缓存判定，允许未命中，不能错误复用。

建议缓存范围先限定在当前工作区、会话及同一份源码的工作状态内。
缓存有容量与回收边界，进程重启后允许失效；不承诺跨源码或跨会话复用。
缓存依赖已回收文件时，能从有效内容恢复则恢复，否则转为未命中，不返回悬空路径。

### 查询按采集批次复用

相同 Intent 在不同时间可能读到不同结果，Intent 校验键只证明定义一致，不能证明数据新鲜。
首次运行创建采集批次，之后改稿默认复用该批次已经取得的未变查询结果：

- 改 jq、模板或业务说明，复用已经采集的数据。
- 改 Intent 或新增查询，在实际执行时采集并记录时间。
- `refresh: true` 新建采集批次，重新执行查询，再按新输入检查加工缓存。
- 模型、数据源配置等相关环境变化，对应查询缓存失效，回执说明原因。

批次表示改稿期间的复用范围，不代表数据库事务快照。
不同查询可能在不同时间取得，缓存回收后的重查也须明确标记。
显式上下文时间应在采集批次内固定，新批次重新捕获，具体入口见待补齐事项。

## 七、意图与来源链

源码 DAG 描述计划怎样处理数据，`origin` 记录结果实际怎样取得。
每步的业务意图建议写在对应 `let` 前紧邻的行注释中，工具提取关联说明，不要求重复填写依赖。
asset 所属章节的标题和散文解释方法与表达设计，不再自动作为每个处理节点的意图。
一个 asset 被多次使用时，各 binding 可以有不同业务意图。

来源链必须保留：

- 给定数据的实际内容与性质，查询实际执行的 Intent、模型身份及观察到的数据来源。
- 实际执行的 jq、业务意图，以及具名输入与其完整上游。
- 参数投影对应的上游根与实际选择路径；切片不切断上游来源，缓存复用也须保留本轮绑定与路径。
- 实际使用的绘图规格、模板绑定，图表和正文标量各自的数据来路。
- 程序所属源码及 asset 名，并随来源保留实际代码，源码文件删除后仍能解释结果。

本轮运行记录保存源码摘要、binding 与资产的对应关系、节点结果身份和缓存复用信息。
注释或名字变化时更新本轮关联，已有查询的真实采集时间、实际来源及原始记录保持准确。
缓存命中不能写成重新查询；已有交付结果不会因源码继续编辑而被改写。

持久化报告沿用现有自足归档：最终展示数据、完整来源链，以及从链中提取的实际 jq 共享代码。
文档的 `assets` 是创作资源区，报告读模型的 `data.assets` 是现有归档结构，两者职责分别保持。
报告无须携带全部备选源码或通用中间输出；是否附整份回答源码及其自动缩水另议。

## 八、普通回答、持久化与回执

末尾结果由 `render_html` 形成，普通回答与报告共用 XHTML 数据引用和来源绑定。

- `delivery: "reply"`：适配为宿主可展示的对话内容，返回给 Agent 交付，不登记 HTML 报告资产。
- `delivery: "artifact"`：输出自足 HTML 报告，按现有产物机制登记并返回路径。

需要明确对话呈现的支持子集，不能假定宿主直接显示 XHTML。
超出呈现能力的元素须给诊断；最终文字超过预算时应调整规模或改用报告交付，不能把截断内容视为完整答案。

运行器自动管理中间结果物化和回收，Agent 不逐步指定保存路径。
缓存命中不重复写中间材料；已有材料回收时按有效内容恢复或重新执行。
普通回答不生成报告文件，但源码、运行状态和内部数据仍可在保留期内存在。
对话结果带运行身份，以便在保留期内追踪；持久化报告继续依靠自身内容解释来源。

回执保持有界，提供：

- 源码摘要、运行身份、采集批次、整体状态及末尾结果是否就绪。
- 根据变量引用生成的流水线摘要，以及各 binding 的 `executed`、`cached`、`failed`、`blocked` 状态。
- 查询实际采集时间、缓存复用来源，以及重新采集的原因。
- 适用的 shape、行数和可交给 `oks_data` 阅读的资产路径。
- 指向 pipeline 或 asset 在原 Markdown 中位置的诊断；jaq 运行时没有源码位置时如实保留限制。

完整数据不逐项展开到回执。Agent 可用现有 `oks_data` 查看中间结果；
若查看中产生的方法成为答案依据，则应写回 pipeline 与对应 asset。

## 九、实施边界与验收方向

本轮只拟增加业务回答的编排层，保留源码外的知识发现与结果读取工具。
实现时应提取共享查询、加工、渲染函数，再增加 Markdown 提取、流水线解析和运行状态。
工具协议与流水线共用业务能力，避免输入形状、校验和来源链形成两套契约。

后续验收至少覆盖：

| 场景 | 期望 |
| --- | --- |
| 完整源码反复提交 | 全量检查，逐 binding 命中缓存，不重复查询或物化 |
| 修改单个 asset | 使用该内容的计算及下游正确检查缓存 |
| 重命名 binding／asset 或修改说明 | 输入接口与内容不变时计算可复用，本轮来源关联准确 |
| 同一 asset 用于多个 binding | 按各自实际输入计算，意图与来源分别正确 |
| 具名输入简写、显式别名和静态路径 | 依赖与程序可见值一致，路径错误明确，来源保留实际取值路径 |
| 缺资源、语言错配、非法语法、未绑定名字、结果不合法 | 执行前定位到 pipeline 或 asset 的原始位置 |
| 改 Intent、新增查询、显式刷新 | 采集行为准确，未伪称整份回答来自同一数据库快照 |
| 大结果、运行失败或取消 | 错误有界，下游受阻，成功分支可复用 |
| 来源变化而数据相同 | 纯计算可复用，最终产物继承本轮真实来源 |
| 对话与 HTML 交付 | 相同证据和绑定，呈现和持久化各自正确 |
| 缓存回收、进程重启、执行期间改稿 | 无悬空路径，结果始终对应本轮固定源码 |

## 十、已确认方向与待补齐细节

已确认的方向：

1. Markdown 只承载从业务问题寻求答案的过程，知识掌握与发现留在外部。
2. pipeline 用 let binding 定义计算，变量引用自然构成 DAG，末尾表达式指定最终结果。
3. assets 用独立具名代码块保存数据、Intent、jq 和 XHTML 等原始内容；输入投影由参数中的静态路径表达。
4. 每步计算独立缓存；每次求值完整源码，改稿默认复用采集结果，显式刷新时重取。
5. 普通回答与报告共用模板及来源链，中间结果由工具自动管理。

进入实现前仍需补齐：流水线完整语法与操作签名、业务意图注释的精确提取规则、
显式时间上下文入口、对话呈现子集、缓存预算及运行状态保留周期。
本稿明确整体模型，尚不作为可直接照做的完整协议。
